## 1. 規則（使用者 2026-10-28 提出）
1. 使用者每回報一次 push 成功，「push 次數」＋1，修改記到第 3 節。
2. push 次數滿 2 → 更新本檔（push 次數歸零、更新次數＋1）。
3. 更新次數滿 3 → 重新產生 `QUICKSTART.md`＋`PROJECT_CONTEXT.md`（**合併改寫，不要再疊增補**；縮小時不可刪還沒做的項目）並重置本檔。
4. 使用者說「更新文件」「更新生成後.md」可提前（視同一次更新）。
5. 換聊天室先問「上次產生文件後 push 了幾次」。
6. 六份 .md 只在使用者要求時才 commit；重新產生那次 push、只更新 .md 的 push 都不計入。
7. 確認 push 成功看 `git log --oneline -3`（最上面有 `(HEAD -> master, origin/master)`）。
8. 一次 push 帶兩個 commit 只算 1 次；更新本檔的那一刻 push 次數歸零。
9. **`未來目標.md` 是使用者所有未完成目標的總清單，獨立於兩份主文件：重新產生 `QUICKSTART.md`／`PROJECT_CONTEXT.md` 前必須先逐節對照它，不可漏掉任何待辦；它只增不刪（完成的搬到它的第 12 節、使用者說不做的搬到第 11 節）；使用者提出新目標或某目標完成／決定不做時，順手更新它。** 只動它的 push 不計入次數。
10. **`連帶關係圖.md`**：每次新增或改動觸發器、函式、表、共用元件、共用 hook、`localStorage` 鍵時，順手更新它；AI 動手改之前先查它列出「還要一起改哪些檔」。只動它的 push 不計入次數。

### 3.4 教訓（累積）
- AI 交付含「拿掉東西」的修改，要自查有沒有留下未使用變數（TS6133 視為 build 錯誤）；**「換掉 N 行」要把緊接著的舊行一併列出，否則會留下重複宣告（2026-11-16 實例：`const err` TS2451）**。
- 交付檔路徑一律先對照 `git status` 實際路徑（2026-11-16 實例：`GlossaryAdmin.tsx` 在 `src\components\`，AI 曾寫成 `src\`）；交付後請使用者貼 `git status` 核對。
- 驗證指令跑出「還在」時，先確認檔案是否已存檔再判斷。
- 深色模式覆蓋寫死色碼前要先看實際 DOM 與樣式檔；沒有範圍 class 的元件要另外處理。
- Bilibili 等第三方站會封鎖雲端機房 IP，先查 Logs 再決定放棄。
- SQL Editor 整批執行後段出錯時前段也可能回滾；**SQL Editor 沒有登入身分，`is_admin()` 會失敗**；管理者函式要拆「內部核心＋管理者包裝」才能測試。
- `Select-String -Path` 不能直接遞迴，要用 `Get-ChildItem -Recurse | Select-String`；終端機會把長行切斷，判斷以檔案內容為準；PowerShell 顯示中文註解亂碼只是編碼顯示，不是檔案壞了。
- 改「刪除路徑」類的函式（只動某一 kind）時，要回頭檢查 `gameCleanup.ts` 這類呼叫端有沒有跟著涵蓋新類型。
- 新資料表要同步 `privacy.html`、刪帳號函式與垃圾桶清理；SQL 欄位假設先查 `information_schema.columns`。
- 驗證寫入類功能：結果沒變不等於成功，要實際觸發一次；SQL 檔重跑前先確認不會「constraint already exists」。
- 使用者上傳的檔案有時只有路徑、內容沒進對話；先用 bash 查 `/mnt/user-data/uploads/`，不要直接說沒收到。
- 先查再動手：改函式前請使用者貼線上定義，不憑文件猜函式名稱與欄位；主文件沒記載的程式呼叫要標［待確認］。
- 使用者說「畫面太亂、分不清用途」時，優先合併功能入口，而不是再加分頁。

## 4. 文件瘦身與拆檔計畫（2026-11-11；**使用者 2026-11-15 回「照建議」＝第七次合併不拆檔，之後是否拆檔未決定**）

### 4.1 為什麼要做
- 變大是因為每次合併都在「疊加」。越大，AI 每次讀取越耗額度。過程、commit 流水帳、舊測試結果留在 git log 就夠。

### 4.2 拆檔後的檔案地圖（行數是估計）
**每次開工必讀（要短）**：`QUICKSTART.md`（現況，300 行內）、`使用者決定.md`、`合作規則.md`、`未來目標.md`（只留未完成與未決定）、`生成後.md`。
**依工作內容才讀**：`連帶關係圖.md`、`待實測.md`、`陷阱與技術提醒.md`、`資料庫與函式.md`、`功能規則.md`、`規則助手與OCR.md`。
**平常不讀**：`已完成紀錄.md`。

### 4.3 合併時的縮小規則
1. 已完成且穩定的功能只留「現在怎麼運作」兩三行。
2. **絕對不可刪**：還沒做的項目、使用者決定、未決定的設計、［未驗證］標記、尚未確認的風險；先逐節對照 `未來目標.md`。
3. 同一件事只寫在一處，其他地方寫「見某檔第 N 節」。
4. 每份檔頂端放兩行：本檔放什麼、什麼時候讀，以及檔案地圖。
5. 拆檔後第一次合併，列「章節對照表」給使用者檢查。

### 4.4 日常維護方式
- **小修改**：使用者貼那一段，AI 給「找這句、換成這句」。**大合併**（每三次更新一次）：整份重寫。AI 交付腳本前要說明有沒有試跑過；使用者用 `Select-String` 驗證、確認檔案不是空的。
